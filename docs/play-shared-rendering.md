# Shared battlefield rendering and editing (CT-12–13)

This slice adds organization protocol v2 and a coherent Unity receive mailbox,
then integrates the normal owner and flat group rendering/gestures. Default normal
game activation is an explicit later gate, not an implication of compilation or
fixture success. V1 remains available for the earlier integration harnesses.

## Correlation and ownership

Organization v2 requires `gameplay_revision` on every snapshot. Its independently
generated Java/C# schema and contracts preserve the reviewed v1 contract. V2 uses
the same strict semantic validation after validating its own wire shape. Command
receipts carry no object mappings and admit historical basis only for a known
pending command in the current authenticated session.

`ClientOrganizationSession` has one current and one future snapshot slot, each
bounded by the 256 KiB organization contract. Only an exact current gameplay
revision can produce a `ProjectedOrganizationFrame`. A newer game frame revokes
old geometry immediately; stale organization is dropped and future organization
waits for its game frame. Current/future conflicts reject; matching duplicate
snapshots do not recreate the projected frame. Context admission verifies visible
battlefield object references and current controllers. Surface/session retirement
clears state and completes any pending operation as failed.

Organization packets are intercepted before legacy gameplay-envelope dispatch.
There is one reader and one serialized transport writer. A distinct single pending
organization command never acquires or completes a native command reservation.
The receiver coalesces organization outside the gameplay update/receipt queue.
Host submission additionally requires the exact gameplay revision to be presented
by its captured surface ticket. No network read or socket write runs synchronously in a pointer handler.
Bounded command serialization and operation validation occur before queuing the
transport write; snapshot parsing remains on the receive path.

The shared v1/v2 corpus is generated by `generate_play_organization_fixtures.py`.
`OrganizationV2Checks` covers the wire boundary, historical retries and a single
recipient with two roster seats. `OrganizationReceiveTests` covers the C# corpus,
arrival order, reference rotation, stale/conflicting/hidden/foreign mappings,
pending receipts, future replacement and disposal. Suites run only in Actions.

The private bootstrap can explicitly opt into organization version 2. Missing
configuration retains strict legacy receive behavior and sends no capability probe.
The authentication transcript and protocol-1 game envelopes remain unchanged.
The connected roster and the set of organization recipients are distinct: AI seats
never require a fake socket or viewer context. Wire root insertion indexes count
only admitted members; the host translates them around unadmitted/ineligible root
entries without exposing hidden membership counts. During an unavailable native
basis, historical retries still return their original receipt and new rejections
remain bounded and recorded in the independent command ledger.

## Normal owner integration

`run_live_game(..., organization=True)` is the explicit acceptance-candidate opt-in.
It puts organization version 2 into both private inherited bootstraps. The global
`SHARED_ORGANIZATION_ENABLED` default remains false until the rollout gates pass.
No keys or capability configuration are passed on command lines or in public game
packets. Without the opt-in, both Java and Unity retain their legacy wire path.

Normal organization uses the existing gameplay owner and writer, not a replacement
multiplayer session. Every published actionable or observer projection captures its
own native-to-opaque bindings. The normal endpoint reads battlefield generations,
controllers and eligibility through bounded authenticated owner metadata requests,
each verified against the same paused cycle. It stages registry reconciliation and
viewer payload validation before adoption. It never exports raw state or native IDs.

Organization reads are consumed before native dispatch and do not consume native
retry slots, offers, receipts or auto-payment reservations. The read loop uses a
32-packet/second extension budget and still services native idle polling. A busy
native advancement can delay organization confirmation; Unity displays pending
feedback and does not commit optimistic geometry. A missing safe basis causes
legacy placement and bounded recorded rejections; historical retries remain valid.

`NormalOrganizationChecks` exercises real guarded metadata with one human recipient
and human/AI roster seats. The native two-client suite also runs in v2 mode and
checks each snapshot's exact gameplay revision. These are separate from packaged
Unity and normal saved-deck human-versus-AI completion evidence.


## Flat-group presentation candidate (CT-12–14)

`ArenaGameplayPresentation` now implements `IOrganizationPresentation`. The live
scene supplies only `host.OrganizationFor(thePresentedGameplayRevision)`. An
opted-in private v2 bootstrap constructs `BattlefieldOrganizationRenderer`; legacy
bootstraps construct no organization renderer. The normal launcher default is
still disabled. This is an acceptance candidate, not enabled shared multiplayer.

The renderer borrows existing surface-owned CardViews and applies final geometry.
It never reparents, binds, duplicates, disposes or resolves artwork for those views.
Groups are flat panels with names, admitted member counts and untapped counts.
Each seat has a separate lane; ungrouped cards and groups occupy separate horizontal
regions to avoid requiring two full card rows at 720p. Paging leaves every member
reachable, including individual attached or tapped permanents. Targeted/selected
decision members choose their page. Combat/target links use a final visible-view
anchor resolver; paged-out members have no fabricated card anchor in this slice.
Group drawers and collapsed-member anchor/access behavior are subsequent CT-15 work.

Shift-click or Shift-Space toggles organization selection. An ordinary click keeps
its existing gameplay path. Dragging a selection past the existing 10-unit
threshold cancels the board gesture before taking capture. Drop on an owned group
to move members; drop into empty group space to name a new group. Creating with a
selection sends create first, then membership only after the authoritative group
snapshot arrives on the same basis. Group headers drag by the original grab offset.
Members are submitted in current admitted order, not hash-set iteration order.

The group action menu exposes rename, delete, order and move-selection operations.
F2/Delete and arrow keys work on focused owned group headers. Opponent headers
have no edit controls; authority remains enforced independently by the host.
Mandatory decisions, reveals, public-zone browsing, inspection, HUD editing and
completed games suppress editing. No organization gesture sends a native game
command. Rejections keep authoritative geometry and show retry feedback. The local
Default arrangement toggle restores legacy geometry without changing shared state.
Missing or revoked organization also restores legacy placement. Surface retirement
clears chrome, selection, pages and drag state without disposing borrowed cards.

### Evidence and remaining acceptance

Hosted `SharedOrganizationPresentationTests` uses two authenticated fixture sockets
with different viewer/object references. It covers shared rename through UI controls,
Shift-selection without a native command, rejected UI membership edits, header drag commands, session retirement, independent
card ownership, attached/countered mixed-tap members, four viewport sizes, missing
organization and legacy fallback. Owner/opponent screenshots upload under
`SharedOrganization/`. These fixtures do not prove native two-player interaction or
normal saved-deck human-versus-AI completion. Run all suites only through Actions;
rebuild the local Windows player after Unity edits.

Manual acceptance before enabling normal games:

1. In an explicitly v2-enabled native match, play three visible permanents. Shift-
   select two, drag into empty group space, name it Mana Rocks, and confirm. Confirm
   both viewers see the same name, ordered members and position; no game action fires.
2. Drag the header, rename with F2, move one member out, then delete a populated
   group. Confirm the opponent cannot edit it and all cards remain independent.
3. Tap one member, add counters/attachments, then target, activate and attack with
   individual members. Page through a dense group. Open inspection and the HUD editor;
   confirm organization gestures cannot steal their input or a mandatory decision.
4. Resize through 1280x720, 1366x768, 1920x1080 and 2560x1440. Toggle Default arrangement,
   advance game revisions, and close the session while dragging. Confirm no stale
   chrome, capture, card bindings or artwork survive retirement.

Still required: packaged native organization rendering/edit acceptance, normal
saved-deck full-game evidence, dynamic drawers/local collapse (CT-15), reconnect
reconstruction and join/leave policy (CT-16–17), and measured accessibility/performance
release gates. Four-player composition remains CT-24. No rollout flag is enabled
by this commit.
