# Release versioning

- Manaforge is in prerelease development. Keep new versions labelled `-alpha.1` (or `-beta.1` once the user chooses beta); do not publish a stable release without explicit instruction.
- Before each requested implementation/documentation commit, increment the patch component of `APP_VERSION` in `Mtg_Projects/mtg_proxy/constants.py` and include it in that commit. For example, `0.2.1-alpha.1` becomes `0.2.2-alpha.1`.
- When merging a development branch into `main`, increment the minor component and reset patch to zero, retaining the prerelease label. For example, `0.2.3-alpha.1` becomes `0.3.0-alpha.1`. Include the version update in the merge work before pushing.
- The first prerelease commit after `0.1.1` is `0.1.2-alpha.1`. Do not retroactively change existing tags or releases.
- A version bump does not authorize creating a GitHub release or tag. If publishing is requested, mark alpha/beta releases as prereleases.

# Continuous development and CI-gated promotion

- Use one active development branch: `codex/play-live-first-land` until explicitly changed. Make small focused commits; isolate work on another branch only when necessary. Keep this branch after promotion. Never indiscriminately merge historical branches.
- `main` is the verified integration baseline. Never force-push, rewrite shared history, bypass protection/reviews, or use checks from an older SHA to promote a newer HEAD.
- At session start read [the workflow guide](docs/development-workflow.md), run `python tools/ci_checkpoint.py status`, and resume the persistent record. After each development commit run `python tools/ci_checkpoint.py checkpoint`. Count commits from Git ancestry, not memory. No local test suites: GitHub Actions is the testing environment.
- Before regular promotions, establish the latest integrated development baseline against the existing playable human-versus-AI acceptance requirements. Opening/fixture success alone is insufficient. Baseline acceptance and applicable CI must both be evidenced. Policy adoption does not authorize merging historical unverified work.
- After three new development commits, capture the exact candidate SHA and inspect its applicable Actions workflows, individual jobs and required steps once. Review the entire `main..candidate` change range, including Python/Core, Java/XMage, Unity, shared protocols, build/packaging and gameplay acceptance/regressions. Repository protection requirements are additional gates.
- Missing, skipped, cancelled or incomplete required workflows/jobs/steps never count as success. Dispatch existing workflows when path filters or manual triggers omit required coverage. Licensing, runner and infrastructure limitations are blocked gates and must be reported.
- If running, retain the candidate and run IDs, continue planned implementation, and inspect once after each subsequent commit. Never poll repeatedly or wait for CI. Preserve unfinished state at session end. A newer HEAD does not replace a pending candidate.
- If red, inspect failing job logs, classify code/test/environment/dependency/infrastructure causes, fix actual defects, commit on the active branch, and validate the correction. Do not weaken tests or promote the failure or unverified descendants. Explicitly supersede the failed candidate with the correction SHA while retaining its audit history.
- If green, review exact-SHA evidence, current `main` ancestry, acceptance and protection/reviews. Promote only that SHA, preferably by fast-forward where permitted; otherwise use the approved PR flow pinned to that candidate. Never delete the development branch. Record successful promotion and resume the three-commit cadence from the development HEAD at resolution (commits made while waiting do not cause an immediate extra checkpoint).
- Prepare the minor version bump on development **before** freezing a promotion candidate, retaining the prerelease suffix. That commit and any conflict/integration/merge-result commit require their own CI verification before promotion. Do not add an untested version commit to `main` after checking CI.
- Keep unrelated dirty work out of commits and promotions. The helper tracks and captures evidence; it does not authorize merges or certify playable acceptance. Follow the promotion checklist in the guide.
